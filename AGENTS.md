# Nightdrive operating contract

## Authority and scope

Read this file first, then `docs/DECISIONS.md`, `docs/SCOPE.md`, and the document governing the task. If documents conflict, stop implementation, reconcile conservatively, and record any architectural resolution in `docs/DECISIONS.md`.

Nightdrive helps producers create original, editable musical material. Determine current coordination state and the next repository-eligible bounded work from `PROJECT_STATE.md` and `docs/ROADMAP.md`; use Git and authoritative decision, domain, review, and evaluation documents for detailed accepted history. MIDI-004 is accepted only for the declared tested FL Studio environment. Aggregate provenance, structured human evaluation, and later Arpeggiator capability gates retain their separate prerequisites. Do not provision Supabase, deploy to Vercel, install models, or implement note spelling, named intervals, extensions, harmony optimization, production parser workflows, later generation, audio, persistence, or AI features until current coordination state and accepted roadmap scope explicitly identify those capabilities as eligible and their prerequisites are satisfied.

## Non-negotiable boundaries

- The producer remains the composer; do not present output as a finished autonomous song.
- Canonical notes, harmony, rhythm, musical time, and MIDI are produced by deterministic, typed logic—not an LLM.
- Validate AI output against a versioned schema before it can become input to deterministic tools. AI never directly mutates canonical persistence.
- Use explicit seeds and versioned inputs for any randomized generation; retain immutable lineage.
- Use 960 PPQ initially and standard MIDI as the first FL Studio interchange format.
- Locked components must remain byte-for-byte/canonical-value unchanged during unrelated regeneration.
- Prefer a modular monolith. Add infrastructure or dependencies only for a documented need.
- Version 1 is the 8-bar section workflow in `docs/SCOPE.md`; its non-goals are binding.

Once the Product Owner has directed work on Nightdrive, standing execution authority permits Codex to reconcile repository truth, select and prepare the next repository-eligible bounded task, and continue through routine transitions during the active session without another acknowledgement. Completion of one task never makes a future capability eligible by itself.

Stop at each required independent exact-head or consequential contract/architecture review boundary; Codex self-review does not satisfy it. Preserve required review, CI, Build vs. Buy, STOP/BLOCK, scope, and roadmap gates. Stop for a genuine unresolved Product Owner decision about product behavior, architecture, scope, roadmap order, subjective acceptance, consequential dependencies/contracts, conflicting authority, or destructive action outside accepted Git workflow.

It governs execution mechanics only and is subordinate to this operating contract, accepted decisions, scope, roadmap authorization, architecture, testing strategy, formal review procedures, and task-specific authoritative documents. On conflict, follow the existing source-of-truth rule and stop rather than infer.
- Use the [Engineering Review Playbook](docs/ENGINEERING_REVIEW_PLAYBOOK.md) for read-only review procedures when justified by risk/change; reviews inspect and report only. A REVISE finding may lead to a separate bounded correction without another acknowledgement when the accepted contract determines it. This playbook does not supersede AGENTS.md or accepted repository requirements, decisions, architecture, contracts, testing strategy, or milestone eligibility.
- Exact-head review is contract-first: independently compare accepted obligations with candidate behavior, tests, and evidence, and carry applicable unresolved findings across commit or branch changes until resolution is demonstrated. A separate Codex review can inform the required independent reviewer but has no acceptance authority unless an accepted policy explicitly grants that substitution. An incomplete review cannot return PASS.
- A qualified, separate Codex reviewer may satisfy required independent exact-head review within the [settled-contract reviewer substitution gate](docs/AI_ENGINEERING_WORKFLOW.md#settled-contract-dedicated-reviewer-substitution). Changes to governing authority, reserved consequential decisions, incomplete or uncertain review, and unresolved authority conflicts retain the existing external reviewer or Product Owner boundary. - **CANDIDATE — standing qualified-review material egress:** This exact authorization becomes binding only after consequential external exact-head review PASS, then explicit Product Owner acceptance of that exact reviewed tuple, followed by protected integration. External PASS is technical approval only. Before all three conditions are satisfied, it is not authority and cannot authorize review of the candidate that introduces it; no status-only post-review mutation is required for it to take effect.

A new candidate SHA or contract-determined corrective head requires fresh classification and its own immutable tuple review; this egress authorization never makes work eligible or transfers technical PASS. It excludes secrets, `.env` contents, credentials, tokens, passwords, cookies, session/authentication material, environment-variable values, credential stores, deferred stash contents, unrelated local files or logs, personal data unrelated to Nightdrive, other repositories or projects, connected-account data, and unauthorized private external material. If the qualified reviewer cannot inspect already-permitted material because of a sandbox or read-access failure, preserve the candidate and route it as `BLOCKED` through the existing external-review policy; do not request duplicate Product Owner transmission authorization.
- Every terminal or checkpoint result returned to the Product Owner must end with the [USER ACTION REQUIRED](docs/AI_ENGINEERING_WORKFLOW.md#user-action-required-handoff) section. This footer translates an unavoidable stop into a concrete action and must not create a new stop when routine repository-eligible work can continue.
- Before meaningful engineering work, read `PROJECT_STATE.md` when it exists; update it when project coordination state materially changes, replacing stale state rather than accumulating a log. Keep requirements, architecture, contracts, tests, and decisions in their authoritative documents, and use Git for detailed history.
- Trace behavior to requirement IDs and acceptance criteria. Update authoritative documentation with behavior changes.
- Use explicit units, UTC timestamps, stable ordering, typed interfaces, structured errors, and idempotency where relevant.

- Never commit secrets or `.env` contents. Privileged Supabase credentials are server-only.

## Build vs. Buy / Dependency Evaluation Gate

Before implementing any new capability that could reasonably be provided by an established library, framework, protocol implementation, SDK, or standard tool, classify it as Nightdrive-specific domain logic, commodity/standardized functionality, or mixed. Keep Nightdrive-specific semantics owned by Nightdrive; use a mature dependency for commodity mechanisms when it provides meaningful value over a small local implementation. Evaluate candidate dependencies for capability fit, maintenance, license, TypeScript/runtime support, determinism, testability, size/transitives, security, API stability, pinning, canonical-boundary impact, and replaceability. External libraries may implement commodity mechanisms but must not define canonical musical semantics; use adapters where consequential. Do not replace accepted primitives without evidence preserving semantics. Record the classification, alternatives, selected approach, rationale, boundary impact, and dependencies in every implementation report. If no suitable library exists, document why custom code is appropriate. Stop for architecture review if adoption would change accepted architecture, canonical semantics, persisted formats, or public interfaces. Skip broad package research for trivial local logic.

## Delivery report

Every implementation task must report: task completed; files modified; implementation; tests and results; acceptance verification; UX/accessibility verification; architecture/docs changes; Supabase changes; deployment changes; branch; commit; push; assumptions; remaining risks; and the next smallest backlog task. A recommendation alone does not establish repository eligibility for a future capability.
