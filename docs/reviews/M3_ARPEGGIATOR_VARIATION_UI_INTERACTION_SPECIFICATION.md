# M3 first Arpeggiator variation UI interaction specification

Date: 2026-10-11
Status: SPECIFY CANDIDATE. Consequential external exact-head PASS and explicit Product Owner acceptance of this exact candidate are required before local implementation authority under ADR-031. This document does not implement or self-accept UI behavior.

## Authority, decisions and bounded purpose

Read with [ADR-041 and its canonical contract](M3_ARPEGGIATOR_VARIATION_CONTRACT_SPECIFICATION.md), [ADR-031](../DECISIONS.md#adr-031--local-reviewed-checkpoints-and-milestone-level-integration), [Milestone 3 / Stage 11](../ROADMAP.md#milestone-3--locks-and-useful-variations), FR-005/006 and AC-005/006. This interaction exposes only the accepted first Arpeggiator-only variation and retained alternatives. It does not replace their canonical authority.

The Product Owner selected all three proposed interactions: (1) an initially empty labeled integer Seed field and one explicit Create Arpeggiator Variation button; (2) a labeled native dropdown with Original, Variation 1, Variation 2...; (3) keep the explicitly entered seed after success. These decisions settle the seed-field/default and selector-design choices intentionally left open by ADR-041. Existing form, safe-error, source/ancestry, history, async-ownership, keyboard and audition contracts remain in force.

The prerequisite runtime remains separate: complete retained collection bootstrap/verification, attempt creation, alternative append/selection, independent active histories and combined preview must be implemented and reviewed before UI exposure. Existing root/proof and attempt verification alone do not satisfy that prerequisite. No new canonical schema, command, hash domain, admission token or source authority is defined here.

## Surface and initial state

Use a bounded Arpeggiator variations section alongside the existing generation, Lead editing, timeline and audition surface. Reuse current layout and native-control styles; no broader piano-roll or visual redesign. Expose the controls only for the current application when a complete original-source/request and editor history can be supplied to the accepted M3 Node boundary. A browser flag or a self-consistent hash is not sufficient authority.

The creation form contains a visibly associated Seed label, one native input with type=number, min=0, max=4294967295, step=1 and required, and a native submit button labeled Create Arpeggiator Variation. Give the input a unique id/name and associate help/error text through existing form conventions. Its initial application-controlled draft is the empty string. Do not prefill it from the original generation seed, selected variation seed, another field, browser state or a remembered preference. It remains a separate proposal from the original Generate seed. No random, incremented, suggested or hidden default seed; no submission on typing, focus or blur.

The retained-alternative control is a visibly labeled native select, label Active variation. Options use retained sequence as their stable value: Original for sequence 0, Variation 1 for sequence 1, Variation 2 for sequence 2, and so on in retained creation order. Do not use root hash, seed, current array index, note selection or musical equality as alternative identity. Repeated deterministic roots remain distinct options because their sequences differ. The displayed selected option reflects the installed authoritative application selection. No custom selector, rename, eviction, comparison panel, separate confirmation step or keyboard shortcut is introduced.

The original entry retains the existing manually edited Lead/history, not a fresh generated Lead. The term Original labels that retained original alternative; it does not promise that its Lead is unedited or reset it. Preserve all existing Lead controls and selection mechanisms. Switching alternatives uses those mechanisms' existing stable-note handling and fallback when a previously selected note does not exist; this task does not redesign note selection.

## Explicit creation and seed validation

Creation occurs only on explicit native form submission, including ordinary keyboard activation. Require a nonempty ASCII base-10 digit string using the existing Generate whole-number convention, then convert to a number and require a safe integer in 0..4294967295. Leading zeros are permitted digit input; the submitted rootSeed is the corresponding absolute numeric value. Reject empty input, signs, whitespace, fractions, exponent notation, hex, unsafe integers and out-of-range values; no trim, clamp, rounding, truncation, coercive fallback or inherited replacement. Native min/max/step/required affordances supplement, never replace, fail-closed application validation.

Native numeric-input sanitization before text reaches application-controlled state is permitted, consistent with the accepted native-form boundary: if an invalid numeric draft becomes empty before delivery, the application rejects empty and does not reconstruct browser-discarded text. Preserve exactly the application-visible draft after rejection. Do not add raw-keystroke capture, change to a text input, or claim that arbitrary invalid text is preserved by the browser. This rule does not change any existing control or ADR-037 semantics.

A locally invalid draft makes no Server Action call and changes no collection, selected state, attempt, history, preview or audition. Show safe Seed-specific feedback and associate it with the control. The explicit action may remain disabled for a locally invalid draft, but its submission handler must still reject invalid input. Do not disable an otherwise valid Create action merely because the seed equals the original, an earlier seed or the currently selected variation's seed. Same-output and repeated explicit attempts are valid under ADR-041; no UI deduplication or novelty search.

For a valid submission, capture the currently installed retained collection and expected selectedSequence, exact selected combined-state identity and exact selected editor identity under ADR-041. Construct one existing request in its exact order: schema=nightdrive.arpeggiator-variation-request.v1, parent={schema:nightdrive.variation-state.v1,stateHash:<captured selected state hash>}, rootSeed=<explicit parsed seed>. Identities/sequence come from the selected authoritative application response, never from editable text or a guessed hash. Do not add actor/time/sequence, parameters, role selector or source defaults to this musical request.

Use one thin Server Action delegation to the existing M3 pinned-Node application boundary with the retained source, full sourceRequest, complete alternative/proof/history state and captured ownership values. That application boundary owns source admission, sequence assignment, supported metadata acquisition, generation, proof/attempt creation, immutable history fork, selected combined state and derived preview. No new API route, client-side generator, hash engine, second editor, partial root constructor or hash-only authority is permitted. Exact entry-point names may be assigned by their separately reviewed implementation; this specification does not pretend an unimplemented application operation already exists.

The Node boundary must apply ADR-041's exact source replay, full proof, selected-context, stale-parent, seed, metadata, generation, lock/hash and failure-atomicity checks in their existing order. Browser validation is proposal feedback only. Never trust serialized admission claims; no cached server session/registry or lossless-request inference from a malformed collection is introduced. Source admission replay is discarded verification output and must never become a new generated product section or overwrite manually edited Lead/history. Report its one complete-source replay per top-level operation and separate ancestor/target replay cost in implementation evidence; do not claim unmeasured responsiveness.

## Success, retained alternatives and independent history

Install only the complete immutable application returned after successful Node verification, using its returned selected sequence, selected combined/editor identities, complete retained alternatives and derived preview. The newly created alternative becomes the selected returned context under ADR-041; do not install a root, attempt, cursor or preview independently. Creation appends one distinct attempt/alternative and forks the entire selected parent's verified history, including its cursor/redo path, without advancing or truncating the parent's history. It does not manufacture an editor command or Undo step for the Arpeggiator change.

Keep the application-visible Seed draft after successful creation. Selecting another alternative also keeps that draft; selection never silently loads that alternative's seed into the field. A deliberate later Create uses the explicit draft against the then-selected verified parent. Keep original sourceResultHash, protected Harmony/Bass and exact creation-parent edited Lead; retain all prior alternatives and child-owned creation proofs. Canonical actor/time remains the accepted unverified local metadata, not a new user field or authenticated claim.

An explicit Active variation change submits one selection proposal through the same M3 Server Action / pinned-Node boundary pattern, using the requested retained sequence and captured current context ownership. Do not submit on focus or merely rendering options. Selecting the already active sequence makes no call, new attempt, revision or history change. An unknown/malformed sequence or stale expected selection fails closed without changing the installed context. Successful selection restores the selected retained entry's exact current history/cursor and recomputed identical combined state, including its current Lead edits, fixed Arpeggiator and preview. Verification replay verifies the retained proof; it must not install regenerated replacements, append an alternative, assign a new sequence, restamp metadata or reset histories.

Undo/Redo retain their existing editor meaning within the selected alternative. They restore exact existing editor identities/hashes and corresponding combined-state identities; they do not undo Arpeggiator creation or navigate between alternatives. Use Active variation to return to another retained alternative. Editing after Undo truncates only that selected active editor redo path; it never removes another alternative or immutable creationProof, even when both parent and child active histories no longer contain the creation revision. Do not add branch management or a second history system. Existing v1-v7 Lead operations remain compatible; any variation-context wrapper must verify the expected selected sequence and combined/editor parent, reuse existing canonical editor semantics and rebuild the correct combined preview.

The existing CompleteSectionPreview shape remains derived and velocity-agnostic, with its original sourceResultHash. Its Arpeggiator is from the selected verified variation root (or original selected editor track for Original), its Lead from the selected verified editor history, and its Harmony/Bass/section from the protected verified state. Never display or audition the old editor application's original-Arpeggiator preview as the current varied composition. No velocity/gain, voice, scheduling, Loop, role-isolation or transport-contract change.

## Pending ownership, rejection and audition

Reuse the existing editor in-flight guard and async ownership/epoch mechanism across generation, variation creation/selection, Lead edits and Undo/Redo. Permit only one application-changing request in flight; prevent duplicate submit and concurrent context-changing dispatch. While pending, mark the relevant form/section aria-busy and disable its Seed/Create/Active variation controls and conflicting existing application-changing actions using the existing pending pattern. There is no optimistic canonical update, automatic retry, cancellation API, queued replacement or hidden regeneration.

A response may install success or safe failure only while its invocation owns the current epoch and captured source/selected context. New generation inputs, source replacement, accepted context change or unmount invalidate older ownership under the existing rules. Programmatic or other reachable proposal/context changes must not permit a stale response to overwrite newer drafts/selection/state. Ignore stale success/failure without automatic resubmission. Do not impose a new global focus or transport state machine.

On rejection, install none of the proposed root/attempt/history/hash/preview values. Preserve the prior complete authoritative application, alternatives, selected sequence, all history/redo paths, source, preview, and exact application-visible Seed draft. Restore the dropdown display to the still-installed selected sequence. Preserve audition state except for behavior already required by existing error handling; do not automatically stop or restart merely to report a local invalid seed. Map recognized seed failures to safe Seed-relevant feedback and otherwise use a safe variation-operation diagnostic. Do not expose raw exceptions, stack traces, filesystem paths, internal proof objects or private diagnostics. A proof/admission/runtime failure never receives a hash-only fallback or an unsupported browser-permission diagnosis.

Successful creation/alternative selection/Lead edit/Undo/Redo uses existing playback invalidation: cancel/stop owned playback and reject stale callbacks before installing the changed selected context, then remain stopped until explicit Play. No automatic start/resume. Typing the Seed or focusing the selector creates no canonical change and submits nothing. Reuse existing controls and transport behavior rather than new audio scheduling or timing policy.

## Keyboard, focus and required evidence

Use associated visible labels, ordinary native tab order and button/form/select keyboard semantics. No pointer interaction is required for seed creation or alternative selection. Provide visible focus using existing styles; feedback is reachable/associated and operation status uses the current safe accessible status/error pattern. Do not move focus to a piano-roll note or selected option automatically on a completed operation. Keep labels and controls available in the current desktop-responsive layout without a wider design project. This defines applicable functional evidence, not full AC-027 or broad device qualification; Narrator-specific checks removed by Product Owner direction are not reinstated.

A separately eligible implementation must independently demonstrate:

- Initially empty labeled native numeric Seed with exact min/max/step/required, unique id/name, one Create action; labeled native Active variation select, Original and all retained sequence options in order. Existing Lead/timeline/audition controls remain.
- Positive 0 and 4294967295, leading-zero digit parsing and ordinary valid seed; empty, signs, whitespace, fractional, exponent, hex, unsafe and out-of-range draft rejection; browser-sanitized invalid draft fails closed with no Server Action and exact application-visible draft retention.
- No submission on typing/blur/focus; one valid explicit request with exact existing parent/seed fields and one thin Server Action delegation; no same-seed/no-musical-change UI rejection; one successful appended attempt and selected complete application without extra editor revisions.
- One full original-source admission per top-level operation, full root/recursive proof and each active/saved history verification, exact expected selectedSequence and combined/editor identities, trusted metadata/sequence ownership and immutable atomic failure. No forged source/hash/flag shortcut. Preserve all F1/F2/F-R1 and M2-EDITOR-REV-001 protections, including duplicate roots with distinct independently valid proof histories.
- Repeated requests retain distinct sequence options and attempts even with identical root/music/IDs/timestamp; seed draft remains after creation and selection. Parent history/cursor/redo, source and protected roles unchanged by creation; current selection comes only from the complete returned application.
- Selection restores exact retained editor and combined identities plus correct preview without new attempt/generation replacement/restamping, and same-selection dispatches nothing. Independent edits/Undo/Redo/redo truncation do not mutate another alternative or discard immutable creation proofs; retain exact closure after both active histories truncate creation revisions.
- Controlled selection and draft preserved on canonical rejection; safe field feedback; duplicate/concurrent dispatch guarded; stale success and failure ignored after source/context ownership invalidation and unmount, without retry or replacement.
- Current varied Arpeggiator and edited Lead in preview, original sourceResultHash and velocity omission preserved; successful context changes invalidate audition and do not auto-Play; explicit later Play uses that installed preview.
- Native keyboard creation/selection and existing edit/Undo/Redo alternatives, associated labels/status, visible focus and bounded responsive behavior in the actual browser. Keep manual/browser observations distinct from automated tests; do not infer them from a static review.

Use accepted independent canonical fixtures and focused generator/editor/Node/Server Action/UI tests as applicable, exact Node24.21.0/npm11.19.0 positive boundary execution, strict TypeScript, changed-file Biome, lint/docs/diff and production build for product source changes. Preserve unfavorable evidence and limitations. Local tests/reviewer PASS never replace external cumulative review against live main, required full pinned PR CI, protected integration or human musical acceptance.
