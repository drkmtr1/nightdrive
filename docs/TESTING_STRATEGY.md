### AC-004 independent reference-vector derivation method

The AC-004 literals require a separately reviewable reference derivation before they can be used as expectations. The reference mechanism is evidence tooling only; it is never imported by production code and it does not define a second product API, schema, policy version, or Harmony theory.

The reference mechanism MUST NOT call `generateStage7ArpeggiatorAggregateV1`, `serializeStage7ArpeggiatorAggregateV1`, `serializeStage7ArpeggiatorAggregateHashInputV1`, either production component-hash helper, the production aggregate result-hash helper, `verifyStage7ArpeggiatorAggregateV1`, either public Arpeggiator generator, the policy resolver/projector, or the production digest adapter. It also MUST NOT invoke Harmony generation. Accepted primitive facts may be reused only as reviewed inputs: the four source-record identities and their exact template/profile/tonic/scale/range choices from `STAGE7_ARPEGGIATOR_GOLDEN_CASES.md`, the accepted literal profile/policy tables and version identities, the accepted component-seed/PRNG algorithms, and the accepted canonical field-order contract. Reuse means copying or independently encoding reviewed facts in the evidence tool; it does not mean importing a production path whose output becomes the oracle.

For each source record, the reference input contains a literal canonical supplied-Harmony context captured from the accepted source record. It records profile, template/version, key, ordered slots, selected voicings, bars and primitive values. The tool verifies that the literal context traces to exactly one accepted source ID and does not call `realizeHarmonyProgression`, select a template, choose a voicing, or reinterpret explanatory Harmony cost/rationale metadata. A changed source context therefore requires an explicit reviewed fixture change rather than silent regeneration.

Expected Arpeggiator events are derived in an independently encoded test-side path: validate the closed profile candidate/weight literals, derive the fixed `arpeggiator` component seed using the accepted versioned byte layout, execute the accepted Mulberry32 transition and exactly five ordered decision draws, apply the reviewed weighted-choice arithmetic and semantic gate mappings, then perform the accepted mask traversal, octave expansion/filtering/deduplication and event timing projection. The reference path owns no new policy; its tables and algorithms are checked against the accepted contract and are never imported from the production resolver, projector, or generator. It emits the event array as literal evidence only after the independent derivation is complete.

Reference canonical JSON is constructed from an independently built, contract-ordered plain record. Its order is the accepted top-level order through `warnings`, with the `resultHash` key omitted for the aggregate-hash input and appended last only in the complete result. Section, minimal supplied Harmony, provenance, component hashes and events use the exact accepted nested field and array order; primitive wire embeddings are independently assembled from their accepted values, not obtained by calling production serializers. The reference encoder uses ordinary `JSON.stringify` only after that object has been independently constructed and structurally checked. It emits UTF-8 without BOM, indentation, insignificant whitespace or terminal newline, with exact ECMAScript JSON escaping, minimal safe-integer decimal forms, and accepted negative-zero normalization. No caller `toJSON`, object-enumeration order, runtime metadata or environment value participates.

The independent digest oracle uses a standard platform SHA-256 implementation in the evidence tool, not the Nightdrive adapter or any production hash helper. Before deriving Nightdrive values, it must pass fixed public SHA-256 known-answer vectors (including the empty string and a non-ASCII UTF-8 string) and compare both hexadecimal spelling and byte length. It then hashes the independently constructed component inputs and result-hash input exactly as specified; all expected digest strings, complete JSON and UTF-8 byte lengths are captured as literals, never generated at assertion time.

Acceptance proceeds in separate, reviewable phases: (A) derive events, normalized JSON, bytes and all three digests with the independent mechanism; (B) capture immutable literal vector records with source identity, versions, request values, expected events, JSON, lengths and digests; (C) human/ChatGPT review the literal records and source traceability; (D) independently recompute the digests and byte lengths with a second invocation/standard implementation; (E) only after literals are frozen, compare production aggregate output against them and report any disagreement as a defect rather than updating expectations; and (F) execute the frozen literals unchanged in fresh Windows ARM64 and Linux x64 Node `24.21.0` processes. A production match is confirmation, never derivation or acceptance by itself.

The mechanism remains retained evidence/reproducibility tooling after the literals are frozen, but normal tests read committed literals and never regenerate or rewrite them. Any literal, source snapshot, algorithm copy, or expected digest change requires explicit review and a new evidence commit; no update flag, snapshot mode or automatic expectation-writing path is permitted. The required matrix remains exactly 16 medium/medium vectors (V1/V1 and V2/V2 × four accepted profiles × roots `0` and `0xffffffff`) plus at least one non-medium V1/R1-distinguishing vector. This method specifies the prerequisite evidence only; it does not generate vectors, execute AC-004, or claim Stage 7 completion.

### AC-004 canonical Harmony snapshot capture and freeze

The four accepted source records uniquely determine their supplied Harmony contexts. Each fixes the profile, canonical template ID/version, tonic `PitchClass 0`, template scale, eight-bar timing, ordered progression template, and the accepted deterministic Harmony realization rules. No seed, alternate template, or caller-selected voicing is required. The accepted cases are `dark-synthwave-chorus-001`, `classic-synthwave-chorus-001`, `darkwave-verse-001`, and `cyberpunk-build-001`, as recorded in `STAGE7_ARPEGGIATOR_GOLDEN_CASES.md`.

One-time snapshot capture may therefore run the already accepted deterministic Harmony reconstruction path for exactly those four source records. This is an upstream evidence-input operation, not an aggregate oracle: it makes no new musical choice and does not derive Arpeggiator events, canonical aggregate JSON, component hashes, or `resultHash`. Production Harmony realization is permitted only for this one-time materialization because the source identity and all inputs are already accepted and the captured result is subsequently detached from live generation.

Each captured literal snapshot must contain exactly the traceability ID and canonical supplied-Harmony values needed by the aggregate reference method: `profile`, `templateId`, `templateVersion`, canonical `key`, and ordered `slots`; each slot contains `index`, `degree`, `bars`, canonical `chord`, canonical `inversion`, and selected canonical `voicing`. Primitive values use their accepted fields and ordering. Explanatory Harmony cost, rationale, tie-break and other realization metadata are not snapshot state; any source citation needed for review is kept as adjacent traceability metadata rather than embedded canonical Harmony.

Capture and acceptance are separate phases. (A) Run the accepted reconstruction for one exact source-record tuple. (B) Detach and write the complete literal snapshot to the existing evaluation evidence location `src/evaluation/stage7-ac004-harmony-snapshots.ts` (or its directly reviewed equivalent), with one named record per source ID and recursively frozen ordinary values. (C) Independently inspect the literal against the source record, profile/template compatibility, Key/template scale, ordered slot indices and bars, chord qualities, inversion domains, selected voicings, eight-bar bounds and existing Harmony validators/contracts. (D) Review the complete literal diff and source traceability. (E) Freeze the snapshot in a dedicated reviewed evidence commit. Future reference tooling reads these literals and never invokes Harmony generation, changes them, selects an alternate voicing/template, or reconstructs a replacement context.

Snapshot literals are evidence inputs, not production persistence, a new Harmony API, a second Harmony source of truth, or authorization for aggregate generation. Normal tests MUST NOT regenerate them, compare current Harmony output and silently accept it, or provide an update/snapshot mode. A changed source record, template, voicing contract or Harmony implementation is reported as snapshot drift and requires a new bounded capture/review task; it must not rewrite historical literals automatically. Future disagreement between a live reconstruction and a frozen snapshot is evidence to investigate, not permission to repair either side silently.

Once accepted, these four frozen inputs are the only Harmony values the independent AC-004 reference-vector mechanism may consume. All existing prohibitions on aggregate generation, Arpeggiator generation/resolution/projection, production serializers, production hash helpers, aggregate verification and live expected-value regeneration remain unchanged. This capture method creates no vectors and supplies no AC-004 acceptance evidence by itself.
